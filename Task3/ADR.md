### <a name="_qmphm5d6rvi3"></a>**Решение**

Для проектирования архитектуры использована модель **C4**, включающая уровни:

- **Контекст (Context)** — взаимодействие системы с внешними акторами.
- **Контейнеры (Containers)** — основные приложения и сервисы.

#### 📌 Диаграмма 1: C4 Level 1 — Context Diagram

**Файл:** `Context.puml`

На диаграмме отображены:

- Внешние акторы: **Новый клиент**, **Зарегистрированный клиент**, **Менеджер кол-центра**, **Сотрудник бэк-офиса**.
- Системы: **Сайт банка**, **Интернет-банк**, **АБС**, **Система кол-центра**, **SMS-шлюз**, **Система управления
  ставками**, **Центр обработки данных (ЦОД)**.

Связи:

- Клиент → Сайт / Интернет-банк (HTTPS, TLS)
- Сайт → Система управления ставками (API)
- Интернет-банк → Система управления ставками, SMS-шлюз
- Интернет-банк → Промежуточный сервис (через очередь или API)
- Промежуточный сервис → АБС (асинхронно)
- Бэк-офис → АБС, Система управления ставками

> ⚠️ АБС **не вызывается напрямую** из интернет-банка — это критично для производительности.

#### 📌 Диаграмма 2: C4 Level 2 — Container Diagram

**Файл:** `Container.puml`

Детализированы:

- **Интернет-банк**:
    - Web/UI-фронтенд (React/Angular)
    - Backend for Frontend (BFF) — API для клиента
    - Служба аутентификации
    - Интеграционный адаптер (для ставок, SMS, очередей)

- **АБС (Автоматизированная банковская система)**:
    - Core Banking Engine
    - API Gateway (ограниченный, синхронный)
    - База данных (Oracle)

- **Промежуточный сервис (Deposit Processing Service)**:
    - Принимает заявки из интернет-банка и сайта
    - Поставляет в очередь (Kafka) или хранит в БД
    - Отправляет задачи в бэк-офис
    - Асинхронно взаимодействует с АБС

- **Система управления ставками**:
    - Веб-интерфейс для бэк-офиса
    - REST API
    - База данных (MS SQL или Oracle)

- **SMS-шлюз** — внешняя система, вызывается через BFF

- **Kafka** — используется как шина событий между интернет-банком и АБС (в будущем). Сейчас — резерв, но закладывается
  архитектурно.

#### 🧭 Логика принятия решений:

- **Асинхронная обработка заявок** выбрана, чтобы не нагружать АБС и обеспечить отказоустойчивость.
- **Горизонтальное масштабирование** реализуется для интернет-банка и промежуточного сервиса (в Docker/K8s).
- **Промежуточный слой (Deposit Processing Service)** — ключевой элемент: он разрывает жёсткую связь между
  интернет-банком и АБС.
- **Централизованное управление ставками** — вынос из XLS в БД (MS SQL/Oracle) с веб-интерфейсом.
- **TLS и аудит** — обязательны для всех точек передачи данных.
- **Kafka** — закладывается как стратегическое решение, несмотря на текущую несовместимость. Используются адаптеры (
  bridge).
- **UI соответствует дизайн-системе банка** — цвета, компоненты, доступность.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| **Альтернатива**                        | **Обоснование отказа / выбора**                                                                                     |
|-----------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| **Прямой вызов АБС из интернет-банка**  | Отклонено: АБС перегружена, масштабируется только вертикально. Риск простоя.                                        |
| **Хранение ставок в XLS-файлах**        | Отклонено: не обеспечивает актуальность, нет контроля доступа, высокий риск ошибок.                                 |
| **Использование RabbitMQ вместо Kafka** | Рассматривалось, но выбран Kafka — стратегическая платформа банка, лучше подходит для масштабирования и интеграций. |
| **Реализация всего функционала в АБС**  | Отклонено: АБС — legacy, медленно развивается. Лучше вынести новую логику в отдельные сервисы.                      |
| **Отказ от SMS-подтверждения**          | Невозможен: регулятор требует двухфакторную аутентификацию для финансовых операций.                                 |

### **Недостатки, ограничения, риски**

| **Аспект**                                                  | **Описание**                                                                                                                                |
|-------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| **Риск перегрузки АБС**                                     | Даже при асинхронной обработке пиковые нагрузки могут повлиять на АБС. Решение: буферизация через очередь и ограничение скорости обработки. |
| **Технический долг интернет-банка**                         | Текущая архитектура несовместима с Kafka. Требуется промежуточный адаптер (HTTP → Kafka).                                                   |
| **Задержки при идентификации**                              | Клиент должен прийти в отделение — это замедляет процесс. Но это требование ЦБ, обойти нельзя.                                              |
| **Ограниченная экспертиза по Kafka во внутренних командах** | Решение: обучение, привлечение экспертов, поэтапное внедрение.                                                                              |
| **Зависимость от команды АБС**                              | Любые изменения в АБС требуют их участия. Решение: чёткие SLA и контракты API.                                                              |
| **Временное решение для MVP**                               | На этапе MVP заявки обрабатываются вручную. Это ограничение, но позволяет быстро запустить. Дальнейшая автоматизация — следующий этап.      |
| **Единый ЦОД для интернет-банка**                           | Пока нет отказоустойчивости. Решение: закладываем мульти-ЦОД архитектуру, но развёртывание — на следующем этапе.                            |
